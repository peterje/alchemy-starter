# Agent guide

This repository is a template. Every file is an example future code will copy, so keep changes idiomatic and delete anything that is not pulling its weight.

## Bootstrap

When someone forks this template and asks you to set it up, follow `docs/bootstrap.md` from zero to a production URL.

## Architecture

- Sign-in is Google through WorkOS AuthKit; which providers AuthKit's page offers is a WorkOS setting, so routes are provider-neutral (`/api/auth/sign-in`, `/api/auth/callback`). AuthKit owns identities and sessions; the API Worker owns the session resource: `apps/api/src/auth.ts` exchanges the callback's code, seals the tokens into an HttpOnly cookie, verifies them on every request against WorkOS's keys, and refreshes them. Endpoints behind the contract's `Authentication` middleware read `CurrentUser`. Local runs and tests use the WorkOS emulator, which `alchemy dev` starts; deployed stages register their callback with `providers/workos.ts`.
- Postgres is the control plane: who exists and what they own, queried across users. Durable Objects are the data plane: one object per unit of hot state, the single writer for it.
- Each stage has its own PlanetScale branch: `prod` serves from `main`, and every other stage, including each pull request, gets an empty branch that Alchemy migrates at deploy time. `apps/api/src/postgres.ts` declares it; the Worker queries it through Hyperdrive with caching off.
- The workspace is split by runtime. `packages/contract` (schemas, IDs, errors, `HttpApi` groups) runs everywhere and depends on Effect only. `apps/api` (the Worker and one file per Durable Object) runs in workerd. `apps/website` (routes, atoms) runs in the browser and SSR. The website never imports `@starter/api`; the Vite build fails if it does.
- A feature is one contract module with its `HttpApiGroup`s added in `api.ts`; a module under `apps/api/src` with its services and its `HttpApiBuilder.group` handlers (`users.ts` is the smallest example), its state in Postgres tables or on the object that owns it; the handlers provided in `worker.ts`, which only composes; and a route under `apps/website/src/routes`.
- Declare a service as `class X extends Context.Service<X>()("X", { make }) { static readonly layer = Layer.effect(this)(this.make) }`, the way Effect's own source does. `make` takes its dependencies with `yield*`, never as parameters, and wraps each method in `Effect.fn("X.method")` so it appears in traces. Other layers are named for what they implement (`UsersHandlers`, `AuthenticationMiddleware`). Postgres queries go through `SqlClient`, which `worker.ts` provides.
- An object that holds a user's data records its owner and checks the caller on every method, answering a non-owner with its not-found error so existence does not leak. The Worker passes `CurrentUser`'s ID into each call.
- Objects are the consistency boundary and expose RPC methods only, never `fetch`. Put state that must be read and written together in one object. Objects raise typed errors; they cross the stub as plain tagged objects, so the Worker handler catches the tag and rebuilds the class. Order cross-object writes so a partial failure leaves unreachable state, never a dangling reference.
- Documents and decks are versioned files. Derive a new file kind's schemas with `VersionedFile` in `packages/contract/src/versioning.ts`, give it an object that owns its tables and runs `applyItemOperation`, and add it to the user's files.
- The UI is [shadcn](https://ui.shadcn.com) on Base UI with Tailwind. Add primitives with `bunx shadcn@latest add <name>` from `apps/website`; they land in `src/components/ui`, which is generated code exempt from the app-state lint rules, so compose them in `src/components` rather than editing them. Style links as buttons with `buttonVariants` on the link itself: Base UI's `Button` gives whatever it renders the button role.
- `atoms.ts` holds the single AtomHttpApi client and the signed-in user atom. Routes read them; they do not create their own.
- `routeTree.gen.ts` is generated by the Vite plugin. Never edit it.
- Change the Postgres schema by adding a numbered file to `apps/api/migrations`, and an object's schema by appending to its migrations list. Never edit or remove a shipped migration.

## Rules

- Effect 4 and Alchemy 2 are newer than most training data. Run `bun run references` to clone the installed versions' source into `.repos/`, and read it, including Alchemy's `examples/`, before writing against an API you are not sure of.

- Application state lives in Effect Atom. Do not use React `useState`, `useReducer`, or `useEffect`.
- Data access goes through the shared `HttpApi` contract. Do not add TanStack server functions.
- Parse input at the I/O boundary with Schema. Do not accept `unknown` or `object` parameters or narrow with `typeof`.
- Every type assertion needs a `SAFETY:` comment stating the checked invariant. Prefer fixing the type.
- Put imports at the top of the module. In a `switch` over a union, add a `never` check in `default`.
- Comments explain why, not what. Keep them for I/O, validation, and edge cases.
- Test pure logic beside it in `*.test.ts`. Test behavior that crosses the Worker, objects, and Postgres in `test/`, against the stack deployed to local workerd. Mock nothing; a test that needs a sleep to pass is wrong.

## Commands

```bash
bun run check               # formatting, lint, types, lint-rule and unit tests, build
bun run test:integration    # deploy to local workerd and test the HTTP API
bun run test:browser        # Playwright against a separate local stage
```
